# Contributing to Docket

Docket is a hobby project. Issues, fixes and widgets are all welcome; there is
no roadmap to fit into and no process to learn beyond this page.

Before anything else, read [NOTICE.md](NOTICE.md). Docket is inspired by
[Dockset](https://dockset.app), a commercial app by an independent developer,
and how this project talks about that is not negotiable: no code, assets, copy
or branding from Dockset ever enters this tree, and nothing here is framed as a
replacement for it.

## Requirements

- macOS 26 or later - `deploymentTarget.macOS` in `project.yml` is `26.0`, and
  the code uses APIs that are not available below it.
- Xcode with a Swift 6 toolchain. The project builds in Swift 6 language mode
  with `SWIFT_STRICT_CONCURRENCY: complete`, so actor isolation is checked, not
  advisory. Most of the app is `@MainActor`; anything crossing a boundary has to
  be `Sendable`.

## Building

`Docket.xcodeproj` is generated by XcodeGen and is **gitignored** - it is not in
the tree, and edits made to it in Xcode are lost on the next generate. All
project configuration lives in `project.yml`.

```sh
brew install xcodegen
xcodegen generate
xcodebuild -scheme Docket -configuration Release build
```

If you change the file layout, add a target, or change a build setting, change
`project.yml` and re-run `xcodegen generate`.

Docket is an `LSUIElement` accessory app: it has no Dock tile and no menu bar of
its own, and its only permanent UI is a status item. It is not sandboxed, and it
requests the Apple Events entitlement (`Resources/Docket.entitlements`).

## Signing

`project.yml` pins manual signing to a specific identity and team:

```yaml
CODE_SIGN_STYLE: Manual
CODE_SIGN_IDENTITY: "Apple Development: ... "
DEVELOPMENT_TEAM: DAK6X938S3
```

Neither will work for you. Replace both with your own, or build ad-hoc with
`CODE_SIGN_IDENTITY: "-"` and no `DEVELOPMENT_TEAM`.

**Know what ad-hoc costs you before you pick it.** macOS will not offer some
permission grants to an ad-hoc signed binary, because there is no stable
identity for the grant to be attached to. Location consent is the one that bites
first: the request returns with the status unchanged and no prompt is ever
shown. If you are working on anything that needs a consent prompt, sign with a
real identity.

Do not commit your own identity or team. If your change to `project.yml` is only
the signing block, leave it out of the diff.

## Tests

```sh
xcodebuild -scheme DocketTests -configuration Debug test
```

241 XCTest cases across six files in `Tests/`. Most of them exist because
something broke - the coordinate round trips and the event-delivery tests in
particular are all scar tissue. Adding to them is the most useful thing you can
do here.

### What a test can actually reach

This is the part worth knowing before you write a test that will not compile.

`DocketTests` does **not** host the app. It compiles a hand-picked subset of
`Sources/` directly, because these are maths and catalog invariants and a test
host would only add launch cost. From `project.yml`:

```yaml
sources:
  - path: Tests
  - path: Sources/Core                            # all of it
  - path: Sources/Widgets/WidgetCatalog.swift
  - path: Sources/DockPanel/DockLayout.swift
  - path: Sources/Services/PollGate.swift
  - path: Sources/DockPanel/ScrollRelay.swift
```

Everything else is invisible to the test target. That includes all of
`Sources/App`, `Sources/MenuBar`, `Sources/NativeDock`, every service except
`PollGate` (so no `WeatherService`, `StockService`, `MusicService`,
`SystemMetrics`), the rest of `Sources/DockPanel`, and **all of
`Sources/Widgets` except `WidgetCatalog.swift`** - no widget views, no detail
panels, no `WidgetContext`.

So if you want new behaviour under test, put the part worth testing somewhere
the test target can see it:

- Pure model, geometry, persistence or layout logic belongs in `Sources/Core`
  or `Sources/DockPanel/DockLayout.swift`, which is exactly why `KeyablePanel`
  and `FirstMouseHostingView` live in `DockLayout.swift` - `InteractionTests`
  needs to build real panels, so the panel types sit in a file the tests can
  import.
- Widget behaviour that is really a rule - defaults, configuration shape,
  category ordering - belongs in the catalog or the models, not in the view.
- If the logic genuinely cannot be moved out of a view, say so in the pull
  request rather than adding the file to the test target and dragging half of
  SwiftUI in behind it.

Adding a path to `DocketTests.sources` is allowed, but it is a real decision:
each one pulls that file's whole dependency graph into the test build. Justify
it in the PR.

## House rules

**Comments explain why, never what.** The code already says what it does. A
comment earns its place by recording the reason - the constant that came from a
measurement, the API that looks wrong and isn't, the defect that a guard exists
to prevent. `Sources/Widgets/WidgetContext.swift` explaining why a card is
tinted black rather than with `Color.primary` is the shape to copy. `// set the
fill` is not.

**New behaviour comes with a test, where the test target can reach it.** See
above. Where it can't, the reason belongs in the PR.

**Deprecated and undocumented APIs are sometimes correct.** `NSAnimationEffect`
is used on purpose - it is the Dock's own poof, and the suggested replacement is
a cursor. Yahoo's chart endpoint is undocumented on purpose, and every field it
returns is handled as optional for exactly that reason. If you touch one of
these, keep the comment that explains it, and keep the failure paths total:
nothing traps, nothing invents a value, a failed refresh leaves the last good
one in place.

**Follow the real Dock, don't copy it.** Size, edge, magnification and auto-hide
are read from `com.apple.dock` rather than duplicated as Docket settings, so
there is nothing to keep in sync. Resist adding a preference that mirrors a
system one.

**Never mention AI, code generation, or tooling of that kind** - not in code,
comments, commit messages, release notes, workflows or documentation.

**If you fork and ship a build**, change the `User-Agent` contact in
`WeatherService` to your own. MET Norway's terms require a real identifier, and
it should point at whoever is actually making the requests.

## Working on an issue

An issue becomes a branch, the branch becomes a pull request, and merging is
what ships it. There is no step in that chain you have to remember, because
each one starts the next.

### Start it

```sh
scripts/start-issue.sh 46
```

That runs `gh issue develop`, which creates the branch **on GitHub, linked to
the issue**. The link is the whole point: a pull request from a linked branch
closes its issue on merge without anyone writing `Closes #46`. A branch you
make yourself with `git checkout -b` has no link and closes nothing.

The script refuses to run if you have uncommitted changes, because switching
branches would carry them across, and that is how work on one issue ends up in
the pull request for another. It also refuses on a closed issue, and if the
issue already has a branch it checks that one out instead of opening a second.

### The branch convention

`<prefix>/<issue-number>-<slug-of-the-title>`, for example
`fix/46-zoomed-windows-run-underneath-the-shelf` or `feat/97-local-iot-hue`.
The number is in front of you the whole time you are on the branch, and
`git branch` sorts into fixes and features on its own.

The prefix comes from the issue's labels:

| Label | Prefix |
| --- | --- |
| `dead-setting`, `unreachable`, `partial`, `wrong-behaviour`, `data-loss`, `polish`, `bug`, `accessibility` | `fix` |
| `enhancement`, `groundwork` | `feat` |
| `documentation` | `docs` |
| anything else, or nothing | `chore` |

An issue with both a defect label and `enhancement` is a `fix`: the defect is
what ships. Doing this by hand is fine, the script just saves you deciding.

### Open the pull request

```sh
gh pr create --fill
```

Small and focused beats large and sweeping. Say what broke and how you know it
is fixed. If it is a behaviour change rather than a fix, say what you tried and
what the alternative was - the reasoning is what ends up in the comment.

**The title is the part that matters.** Commits on the branch can say whatever
you like, but the pull request title has to be a Conventional Commit, because
it is what the release automation reads to decide the next version number:

| Title prefix | What it does to the version |
| --- | --- |
| `fix:` | patch, `0.1.0` to `0.1.1` |
| `feat:` | minor, `0.1.4` to `0.2.0` |
| `docs:`, `chore:`, `refactor:`, `test:`, `ci:`, `build:`, `style:` | nothing, no release |
| `feat!:`, or a `BREAKING CHANGE:` footer | major, and see below |

While the major version is `0`, do not use `!`. Say in the pull request that
the change breaks something and the number gets set by hand, because `1.0.0`
is a decision about the project rather than about one change.

If you squash on merge, check the commit subject GitHub proposes before you
confirm it. With a single commit on the branch it offers that commit's subject
rather than the pull request title, and the automation reads the commit.

### What CI checks

Two jobs, both required, both able to fail you:

- **Build and test.** `xcodegen generate`, then a Debug build of the app, then
  the `DocketTests` suite. The generate step is first and separate: if
  `project.yml` no longer produces a project, nothing after it means anything.
  On a failing test the job attaches the full `xcodebuild` log and puts the
  name of the test that failed in the run summary, so you do not have to go
  looking for it.
- **House rules.** A grep over the files your pull request touches, for em
  dashes and for any line naming the tooling a change was made with. Both are
  rules that rot silently without something checking them. It runs on Linux
  and finishes in seconds, alongside the build rather than in front of it, so
  one push tells you about both.

### Then merge

There is one maintainer, so there is no review to wait for and no approval to
collect. CI is the gate. When it is green, merge, and the issue closes itself.

## Releasing

**Nothing is tagged by hand.** Release Please watches `main`, reads the
Conventional Commit subject of every merge, and keeps one pull request open
with the version bump and the changelog entries those merges have earned. That
pull request rolls forward as more land, so at any moment it is the answer to
"what would shipping right now look like".

Merging it is the release. It commits the new version and `CHANGELOG.md` and
tags `vX.Y.Z`, and the tag is what `.github/workflows/release.yml` has been
waiting for: a universal Release binary with ad-hoc signing, a `.dmg` and a
`.zip`.

So the version is decided by what you merged, not by what you type:

- **Patch** (`0.1.0` to `0.1.1`) from `fix:` titles. Most releases are this.
- **Minor** (`0.1.4` to `0.2.0`) from `feat:` titles.
- **Major** stays at `0` until the app is worth calling finished. Do not use
  `!` to force it, that is a decision about the project rather than about one
  change.

A run of `docs:` and `chore:` merges produces no release pull request at all,
which is correct: there is nothing in them for anyone to download.

Check the release page before you point anyone at it. A generated changelog
says what changed and nothing else, and the part people actually need is the
Gatekeeper walkthrough in `.github/RELEASE_NOTES_TEMPLATE.md`, because an
ad-hoc signed build is blocked on first launch and the old control-click
advice no longer works.

`MARKETING_VERSION` comes from the tag, so the number in `project.yml` is only a
default for local builds and never has to be kept in step.

### Not GitHub Packages

Packages is a registry for dependencies other projects consume: npm, Maven,
NuGet, RubyGems, container images. It has no Swift support, and Swift Package
Manager resolves from git repositories directly in any case. There is nothing
here to publish to it. The distribution channel that does fit a Mac app is a
Homebrew cask, which installs from the release zip.
