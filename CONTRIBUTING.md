# Contributing to Plinth

Plinth is a hobby project. Issues, fixes and widgets are all welcome; there is
no roadmap to fit into and no process to learn beyond this page.

Before anything else, read [NOTICE.md](NOTICE.md). Plinth is inspired by
[Dockset](https://dockset.app), a commercial app by an independent developer,
and how this project talks about that is not negotiable: no code, assets, copy
or branding from Dockset ever enters this tree, and nothing here is framed as a
replacement for it.

## Requirements

- macOS 26 or later — `deploymentTarget.macOS` in `project.yml` is `26.0`, and
  the code uses APIs that are not available below it.
- Xcode with a Swift 6 toolchain. The project builds in Swift 6 language mode
  with `SWIFT_STRICT_CONCURRENCY: complete`, so actor isolation is checked, not
  advisory. Most of the app is `@MainActor`; anything crossing a boundary has to
  be `Sendable`.

## Building

`Plinth.xcodeproj` is generated by XcodeGen and is **gitignored** — it is not in
the tree, and edits made to it in Xcode are lost on the next generate. All
project configuration lives in `project.yml`.

```sh
brew install xcodegen
xcodegen generate
xcodebuild -scheme Plinth -configuration Release build
```

If you change the file layout, add a target, or change a build setting, change
`project.yml` and re-run `xcodegen generate`.

Plinth is an `LSUIElement` accessory app: it has no Dock tile and no menu bar of
its own, and its only permanent UI is a status item. It is not sandboxed, and it
requests the Apple Events entitlement (`Resources/Plinth.entitlements`).

## Signing

`project.yml` pins manual signing to a specific identity and team:

```yaml
CODE_SIGN_STYLE: Manual
CODE_SIGN_IDENTITY: "Apple Development: ... "
DEVELOPMENT_TEAM: DAK6X938S3
```

Neither will work for you. Replace both with your own, or build ad-hoc with
`CODE_SIGN_IDENTITY: "-"` and no `DEVELOPMENT_TEAM`.

**Know what ad-hoc costs you before you pick it.** macOS will not offer some
permission grants to an ad-hoc signed binary, because there is no stable
identity for the grant to be attached to. Location consent is the one that bites
first: the request returns with the status unchanged and no prompt is ever
shown. If you are working on anything that needs a consent prompt, sign with a
real identity.

Do not commit your own identity or team. If your change to `project.yml` is only
the signing block, leave it out of the diff.

## Tests

```sh
xcodebuild -scheme PlinthTests -configuration Debug test
```

241 XCTest cases across six files in `Tests/`. Most of them exist because
something broke — the coordinate round trips and the event-delivery tests in
particular are all scar tissue. Adding to them is the most useful thing you can
do here.

### What a test can actually reach

This is the part worth knowing before you write a test that will not compile.

`PlinthTests` does **not** host the app. It compiles a hand-picked subset of
`Sources/` directly, because these are maths and catalog invariants and a test
host would only add launch cost. From `project.yml`:

```yaml
sources:
  - path: Tests
  - path: Sources/Core                            # all of it
  - path: Sources/Widgets/WidgetCatalog.swift
  - path: Sources/DockPanel/DockLayout.swift
  - path: Sources/Services/PollGate.swift
  - path: Sources/DockPanel/ScrollRelay.swift
```

Everything else is invisible to the test target. That includes all of
`Sources/App`, `Sources/MenuBar`, `Sources/NativeDock`, every service except
`PollGate` (so no `WeatherService`, `StockService`, `MusicService`,
`SystemMetrics`), the rest of `Sources/DockPanel`, and **all of
`Sources/Widgets` except `WidgetCatalog.swift`** — no widget views, no detail
panels, no `WidgetContext`.

So if you want new behaviour under test, put the part worth testing somewhere
the test target can see it:

- Pure model, geometry, persistence or layout logic belongs in `Sources/Core`
  or `Sources/DockPanel/DockLayout.swift`, which is exactly why `KeyablePanel`
  and `FirstMouseHostingView` live in `DockLayout.swift` — `InteractionTests`
  needs to build real panels, so the panel types sit in a file the tests can
  import.
- Widget behaviour that is really a rule — defaults, configuration shape,
  category ordering — belongs in the catalog or the models, not in the view.
- If the logic genuinely cannot be moved out of a view, say so in the pull
  request rather than adding the file to the test target and dragging half of
  SwiftUI in behind it.

Adding a path to `PlinthTests.sources` is allowed, but it is a real decision:
each one pulls that file's whole dependency graph into the test build. Justify
it in the PR.

## House rules

**Comments explain why, never what.** The code already says what it does. A
comment earns its place by recording the reason — the constant that came from a
measurement, the API that looks wrong and isn't, the defect that a guard exists
to prevent. `Sources/Widgets/WidgetContext.swift` explaining why a card is
tinted black rather than with `Color.primary` is the shape to copy. `// set the
fill` is not.

**New behaviour comes with a test, where the test target can reach it.** See
above. Where it can't, the reason belongs in the PR.

**Deprecated and undocumented APIs are sometimes correct.** `NSAnimationEffect`
is used on purpose — it is the Dock's own poof, and the suggested replacement is
a cursor. Yahoo's chart endpoint is undocumented on purpose, and every field it
returns is handled as optional for exactly that reason. If you touch one of
these, keep the comment that explains it, and keep the failure paths total:
nothing traps, nothing invents a value, a failed refresh leaves the last good
one in place.

**Follow the real Dock, don't copy it.** Size, edge, magnification and auto-hide
are read from `com.apple.dock` rather than duplicated as Plinth settings, so
there is nothing to keep in sync. Resist adding a preference that mirrors a
system one.

**Never mention AI, code generation, or tooling of that kind** — not in code,
comments, commit messages, release notes, workflows or documentation.

**If you fork and ship a build**, change the `User-Agent` contact in
`WeatherService` to your own. MET Norway's terms require a real identifier, and
it should point at whoever is actually making the requests.

## Pull requests

Small and focused beats large and sweeping. Say what broke and how you know it
is fixed. If it is a behaviour change rather than a fix, say what you tried and
what the alternative was — the reasoning is what ends up in the comment.
